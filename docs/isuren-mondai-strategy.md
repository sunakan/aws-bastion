# ISUCON過去問をGo版AMIに焼く戦略

## ゴール

ISUCON過去問(isucon14等)をそれぞれGo実装だけに絞り、Packerで自分用のAMIとして焼いて保守する。
Ansible/Taskfileはそのまま使わず、何をしているか分解した上でcloud-init(UserData)とmiseに置き換える。

## bastionの役割

このaws-bastionはお試し用の使い捨て環境。AMI化の対象ではない。
過去問ごとの検証・試行錯誤はここで行うが、最終的なAMIビルドは別の場所(過去問ごとのPacker定義)で行う。

## 進め方(ハイブリッド)

1. **Docker再現で先に動作確認する** (`development/compose-go.yml` 等)
   アプリ自体が正しく動くことを、環境構築の複雑さを気にせず先に確かめる。
2. **Packerでほぼ空の状態で1周させ、ビルド機構自体の疎通確認をする**
   AMI化→起動、のパイプラインが通ることを早期に確認しておくと、後で問題が起きたときに
   「ビルド基盤の問題」か「プロビジョニング内容の問題」かを切り分けやすい。
3. **bastion上で冪等性のあるbashスクリプトを直接試行錯誤して中身を詰める**
   Packerは毎回フルサイクル(起動→プロビジョニング→AMI化→終了)を回すので試行錯誤には重すぎる。
   ubuntuユーザーでbastion上に直接スクリプトを書いて動かし、固めてから次に進む。
4. **固まった内容をcloud-init用に整形する**
5. **Packerに戻して、cloud-initベースの本番相当ビルドを確認する**

途中で1(bashで試行錯誤)と2(Packerで1周)のどちらが効率的か都度見直し、良い方を採用する。

## 個別の方針

- 言語ランタイムのインストールはxbuild(Ansibleが使う独自ツール)ではなくmiseで代替する
- 対象言語はGoのみに絞る(他言語のセットアップは不要)
- 本番の`isucon`ユーザー(パスワードなしsudo)は`isuren`に読み替える。bastion自体のユーザー(user101予定)とは別物
